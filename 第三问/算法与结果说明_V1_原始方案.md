# 第三问算法与结果说明（给论文写作者）

## 1. 第三问究竟比第二问多了什么

原始计算图是有向无环图（DAG）：算子是计算步骤，Tensor 是步骤之间传递的数据。我们提交的是两项决策：每个非 COPY 算子属于哪个子图，以及各核按什么顺序执行哪些子图。官方程序根据提交方案自动处理数据搬运、私有缓存容量、流水线与带宽竞争，输出完成整个计算图所需的周期数 Makespan。

第二问的场景 B 已经规定：同核子图属于同一个 Task，可继续使用该核的 L1/UB 私有缓存；跨核中间数据仍必须由源核 COPY_OUT 到 DDR，经过 500 cycle 同步等待，再由目标核 COPY_IN。第三问保留这一机制，增加所有核心共享的**只读** L2。只有 COPY_IN 会查询 L2：发射时命中就走独立的 L2 读带宽，未命中走 DDR，读取完成后才能插入 L2。L2 满时采用 FIFO 淘汰，命中不会把条目移到队尾。大于 L2 容量的单个 Tensor 不会进入缓存。多核同时请求相同数据时，由于都可能先于第一次读取完成发射，可能全部 miss。

可把 DDR 理解成较慢的公共仓库，把 L1/UB 理解成各核自己的小仓库，把 L2 理解成所有核共用的只读中转货架。中转货架能减少重复读取 DDR，却不能代替所有跨核传输或同步。

例如一个共享输入 T 分别供 3 个核心使用。在没有 L2 时，可能有 3 次 DDR 读取。有 L2 后，理想情况是第一次从 DDR 取，后两次从 L2 取；但若请求同时发射，三次可能都 miss；若中间进入大量其他数据，T 也可能被 FIFO 淘汰。因此“消费者分到更多核”既可能增加并行，也可能增加搬运和等待。第三问的核心是判断某个共享数据应该用**同核 L1/UB 复用**，还是用**跨核 L2 复用**。

## 2. 我们交给官方评估器的是什么

`best_plan.json` 中：

```json
{
  "node_to_subgraph": {"10": 0, "11": 0, "12": 1},
  "core_schedules": [[0], [1]]
}
```

它表示算子 10、11 在子图 0，算子 12 在子图 1；两个子图分别由两个核运行。文件并没有手工指定某个算子在哪个 cycle 发射；最终的 COPY、Cache、Pipe 与 Makespan 均由赛题评估程序计算。每个用例每种核数都保存自己的最终方案和原始评估结果。

我们用 `(Makespan, added_copy_bytes)` 按字典序比较：先尽可能降低总完成时间；若时间相同，再降低额外数据搬运量。Cache 命中率只用于诊断和引导搜索，不凌驾于 Makespan 之上。

## 3. 求解器的完整流程

第一步，以第二问已经评估过的最佳切图与分核方案作为起点，直接用第三问官方程序重新计分。这保证搜索起点具有第二问的通信亲和和 L1/UB 优化，而不是从随机方案出发。1 核时使用整图单 Task 方案，并分别在第二、第三问官方程序中计算无 L2 与有 L2 的成绩。

第二步，建立子图级模型。模型继承第二问的依赖关系、各 Pipe 工作量、关键路径排序、核负载、直接跨核通信以及 L1/UB 压力；再统计每个 Tensor 的大小、生产子图、消费子图及潜在跨核复用。所谓 Hot Tensor，是尺寸较大、被多个子图读取、位于较重要计算路径附近的数据。对于一个大小为 $s$、被 $r$ 个核读取的可缓存数据，理想化复用价值近似为

$$ (r-1)s\left(\frac{1}{60}-\frac{1}{250}\right). $$

这个数仅帮助挑选搜索目标，并不是节省的真实周期数，因为官方执行还会发生并发带宽竞争、依赖等待和缓存淘汰。

第三步，使用一个轻量 FIFO 预测器模拟候选方案的读取顺序，记录预测 DDR miss 字节、L2 hit 字节、被淘汰数据及其尚未完成的读取。若淘汰的数据之后还有多个消费者，就给该候选增加“淘汰损失”。两个读取之间新插入 L2 的总字节数称作字节复用距离；距离越大，第二次读取越可能赶不上 FIFO 留存窗口。预测器把事件简化为顺序访问，所以其命中率只能作为启发式；真实统计始终以官方程序为准。

第四步，生成两类相反但都有理由的结构：**Cluster** 将部分消费者聚到同核，优先保护不能缓存或反复 miss 的共享数据；**Scatter** 将部分可缓存的 Hot Tensor 消费者移往较空闲的核，争取并行与 L2 复用。求解器也复用第二问的通信亲和分核和私有缓存重排，并尝试新的自适应切图。

第五步，在保持 DAG 依赖合法的前提下，从就绪子图中选择执行顺序。优先级综合关键路径、预测 L2 命中收益、FIFO 淘汰损失和 L1/UB 压力。候选集合限制在高关键性的少量就绪子图，不枚举所有合法拓扑序，也不会为了命中率强行把本可并行的计算全部串行化。

第六步，围绕当前最佳方案做有限局部搜索。Move、Swap、ChainMove、Recluster 沿用第二问；ReuseWindowReorder、Cluster/Scatter 为第三问新增。代理分数先排序大量廉价候选，再选少数及一个多样性候选进入官方评估。只有官方 `(Makespan, added_copy_bytes)` 真正改善时才更新 `best_plan.json`。搜索有每配置评估次数、运行时间和停滞轮数上限。大于 1 万算子的图为保证批量可完成，采用已验证的第二问方案作第三问官方评分，不运行成本过高的局部邻域；`summary.json` 中 `search_profile` 会如实标记。

## 4. 为什么不能只看 Cache 命中率

命中率增大不等于总耗时一定下降。假如为了复用一个输入而把原本能在两个核并行的消费者放在一个核，就可能减少 DDR 读取，却让最忙核心变得更慢。反过来，即使命中率不高，合理分散消费者也可能改善核负载。

`case_012` 的 2 核结果是一个例子：无 L2 基线 Makespan 为 25,755；直接把第二问方案放入第三问评估器仍是 25,755；经过 Scatter 类候选及局部搜索，最终为 25,147。官方命中字节率约 8.89%，额外 COPY 字节数仍为 60,120。改善主要体现为调度和并行结构，不能简单描述成“命中率越高越好”。

另一个对照是 `case_010` 的 4 核：第三问最佳方案命中字节率约 41.13%，但 Makespan 只从无 L2 的 23,588 降到 23,574；高命中率本身没有带来同比例的总时长降低。两个例子都说明最终选优必须依赖官方 Makespan。

## 5. 表格和曲线怎样计算

对用例 $i$ 和核数 $k$，记第二问无 L2 的官方 Makespan 为 $M_{i,k}^{(0)}$，第三问只读 L2 的官方 Makespan 为 $M_{i,k}^{(L2)}$。相同核数下的 L2 相对加速比定义为

$$ S_{i,k}^{(L2)}=\frac{M_{i,k}^{(0)}}{M_{i,k}^{(L2)}}. $$

论文报告的平均相对加速比先逐用例求比值，再对全部 100 个用例取算术平均：$\bar S_k^{(L2)}=\frac{1}{100}\sum_{i=1}^{100} S_{i,k}^{(L2)}$。不能把两个 Makespan 总和相除后冒充这一指标。

输出同时给出按核数平均的 Makespan 曲线，以及以**同用例无 L2 单核 Makespan**为共同基准的两条 1～5 核加速曲线。由于不同图规模差异大，平均 Makespan 会受大图影响；平均逐用例加速比更适合比较多核效果。附录表列出每个用例每个核数的两种配置 Makespan、额外搬运量和有 L2 时的官方命中字节率。无 L2 配置不存在 L2 命中率，表格留空，不填造出的 0。

官方 `cache_stats.hit_rate` 是**命中字节率**，即 `hit_bytes/(hit_bytes+miss_bytes)`。`data_movement_bytes.added_copy_bytes` 是额外数据搬运量；L2 命中改变读取路径，却不一定改变同一方案产生的 COPY 字节总量。原始 `best_result.json` 还保留 `per_core_timeline`，可用于进一步分析哪个核是瓶颈、DDR 与 L2 读取何时发生。

## 6. 论文中应怎样表述算法优势与边界

优势在于：继承第二问成熟的切图、直接通信和 L1/UB 优化；把共享数据的 Cluster/Scatter 决策显式纳入第三问；用 FIFO 窗口估计和少量官方评估控制资源消耗；最终成绩可以由原始方案与官方输出逐项复核。算法的目标是在给定预算内找到高质量方案，不是穷举或证明全局最优。FIFO 预测有并发近似误差，大图采用基线评分的资源保护策略，这些都应在论文中如实说明。
